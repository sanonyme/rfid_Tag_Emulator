Three storage systems to keep separate

  • Workshop account database: PostgreSQL inside the dedicated Debian guest, according to DEPLOYMENT.md. This is the game database.
  • Device storage: renderer localStorage for guest collections, local room/day state and account offline caches. Session tokens are in sessionStorage.
  • Supabase install registry: a separate Edge Function and zeus_installs table for installation registration. It is not the Workshop authentication or live-event backend. The app’s Database tool connects to user-configured databases and is also separate.

Working copy versus released product

The package version is 10.3.1, but multiple preview, garden, Christmas and classic installers share that version. An installer version alone does not identify which Workshop features it contains. A classic installer exists in modern-ui/dist-app/workshop-classic/.

Many Workshop changes are modified or untracked in Git, including the entire workshop-server directory. Preserve and commit the current implementation before treating the remote repository as a complete backup. This investigation did not change game code or production data.

Availability and connection selection

The deployment record says the guest, PostgreSQL, app service, host socket and Tailscale daemon start at boot, with Funnel running in background mode. The systemd unit restarts the app after three seconds. Players should not need Tailscale when the public Funnel works. Home power and internet remain dependencies. These boot settings were not re-inspected today.

Endpoint priority is saved Workshop server URL in localStorage, then the Electron main process configuration. The main process uses runtime WORKSHOP_URL ahead of the embedded build default. Both current .env configuration and Vite’s fallback point at the recorded public address. A player’s saved override can therefore keep them on an old server despite a new build.

Remote desktop connections require HTTPS. The client permits plain HTTP only for localhost, 127.0.0.1 or ::1. The LAN HTTP endpoint is useful for infrastructure diagnostics, but the UI rejects it as a normal remote player address.

Connect a player

  • Open Zeus → Workshop → Guest/account → Workshop server.
  • Enter https://proxmox.stalk-great.ts.net:8443 and select Save server address.
  • Switch to General. Confirm the connection is Live and a second independent player appears. Offline solo play can look normal, so visible gameplay alone does not prove a shared connection.
  • Use distinct Electron user-data profiles for two local test players. A second connection for the same account or guest device replaces the first.

Gameplay

Gameplay

The game runs in the React renderer using HTML canvas, a local physics loop and validated gameplay packets. It adds social play to real RFID emulator activity.

Controls and loop

  • Click to walk or use A/D and left/right arrows. Space, W or Up jumps. Equipped wings allow one additional jump in the air.
  • Enter or T opens chat; F throws a snowball; B opens the bag; 1–5 trigger emotes. Click another elf for player actions.
  • Successful Fixed sends and Handheld broadcast rounds emit tags-sent activities. Each completed activity increments sends by ONE; a 1,000-tag batch is one send, not 1,000 event points. Handheld also increments handheld.
  • A send can spawn a shared present, subject to a four-second cooldown and a 12-shared-present client cap. Bigger tag batches improve rarity luck, not the number of sends counted.
  • Walk over a present to open it. It adds a bag item when capacity permits, increments opened, and adds a daily tree ornament. A full bag can still consume a present and increment the counters.
  • Starting or stopping Edge processes rings a bell and increments bells. Starts also affect the daily activity score. Each process activity has a 20% jingle-gift chance. bells is not one of the supported live-event metrics.

Collection and daily gifts

There are 83 item definitions and 17 built-in achievements in this checkout. The normal bag capacity is 240 entries. Trades, returns, starter grants and event rewards can use forced insertion, so 240 is not a universal hard limit. Equipment slots are hat, pet, trail, shirt, wings, mount and title; actual visual/network support varies by slot.

Starter Sprout Wings (leaf-wings) are granted and equipped once when absent from discovery history. Cloud Wings, Ember Wings and Prism Wings are other wing items. Consumables can temporarily change movement, jumping or snowball effects.

A daily personal gift is attempted about 1.8 seconds after the floor mounts. Its streak uses the device’s LOCAL calendar date: minimum uncommon normally, rare from day 3, epic from day 7. These minima are rolled with additional luck. Daily gifts and permanent achievements are built-in game mechanics, not database live-event definitions.

Trades and floor items

Trades offer up to four items per side. Both clients lock in matching terms; the clients apply the collection changes and later synchronize profiles. The server routes packets but does not perform an atomic two-account inventory transfer. A request expires after 20 seconds; idle trades after three minutes.

A floor drop moves an item into local escrow. The owner grants it to a claimant; self-reclaim returns it without increasing given. Giving to another player increments given. Cleanup, disconnects and crashes have different recovery paths; escrow entries are returned on profile load. Avoid treating this client-driven economy as a financial ledger.

Accounts & rooms

Accounts & rooms

Accounts are optional. Guests can play in General and offline; accounts add durable collections, handles, friends, private messages and cloud event rewards.

Signup, login and sessions

  • Signup requires a valid email, a 10–256 character password and one of the seven crews. The name is sanitized and capped at 16 characters.
  • The server hashes the password with a random salt and Node scrypt. It sends an eight-digit Brevo code before creating the actual user/profile/session.
  • The code expires after 10 minutes, permits five incorrect attempts, and is consumed once. Resend waits one minute and permits five sends per hour per address. Failed delivery aborts signup.
  • Verified signup assigns a permanent unique lowercase @handle with a database sequence suffix. Existing accounts are backfilled as elf_N. Renaming an elf does not change its handle.
  • Login returns a 32-byte random token encoded as 64 hex characters. Only its SHA-256 hash is in the database; it expires after seven days. HTTP uses Authorization: Bearer. WebSocket auth is in the hello message, not the URL.
  • The desktop stores the token in sessionStorage. Account caches remain in localStorage. Closing a desktop session returns to the separate guest profile when the session token is gone. Logout attempts server revocation; if the request fails during an outage, local logout still occurs and the server token can remain valid until expiry.

Rooms and crews

RoomAdmission / authority
HomeLocal-only world for this install; no Workshop network requests.
Anexya General · anexya-generalOpen to guests and accounts; no King has moderation authority here.
vsbl / edge / support / cnct / qa / uiOwn-crew signed-in members enter directly unless kicked that UTC day. Others knock and wait for that room’s King.

A guest’s selected crew is only local metadata for event visibility; it does not grant room membership. New accounts choose a crew during signup, so crew membership is not an employer-verified identity claim. Later crew changes are database-owner operations.

Kings are assigned only in the database. A unique constraint permits one King per crew and one crew per King account. Allow/deny/kick is server-authorized for the corresponding crew room. A kick sends the player to General and requires another knock that UTC day. Admission grants expire at midnight UTC. Account grants survive restarts; guest grants and pending guest state do not. The King must be connected in the relevant room to handle the live queue.

Friends and messaging

Friends use permanent account IDs and exact @handle lookup. Requests can be accepted, declined, cancelled or removed. The list is capped at 250 relationships per account. New durable conversations require an accepted friendship.

Private HTTP messages allow 1–1,000 characters and preserve the last 50 messages per account pair, including offline delivery. Opening history marks incoming messages read. The badge counts unread messages plus incoming requests. Only the pair can fetch their conversation. Blocking denies history/messages in both directions and removes friendship; unblocking does not restore it.

The server sends targeted social notifications without message bodies; the UI fetches history over authenticated HTTP, with a 10-second fallback poll. Legacy quick player DMs also exist: if either party is a guest, they are ephemeral; account-to-account quick DMs check blocking but the socket path does not require friendship. Room chat is ephemeral and capped at 80 characters. No end-to-end encryption is implemented; stored messages are database text.

Profile ownership and synchronization

At first login, the device collection is imported once per account, unioned by item UID with newer timestamps winning. Discoveries/achievements are unioned and stats take their maxima. This is not a repeated import of every future guest bag.

Normal online account sync runs about every 10 seconds while admitted inside a shared room. The server locks the profile row and checks an optimistic revision; a stale revision returns 409 and the client reloads/merges. Stats and the latest daily marker do not move backwards. Account caches support offline play and later reconciliation.

Crew, King and owner titles come from database identity, not the submitted profile. A single account or guest device has one active socket connection; another window replaces it. Gameplay packets and profile writes are separate paths, so an on-screen interaction is not proof its account data has already been saved.

What survives a restart

  • Durable in PostgreSQL: accounts, profiles, sessions until expiry, Kings, owner titles, account admission/knocks, event definitions and account progress, account messages, friends, blocks and handles.
  • Only in backend memory: connected players, room trees, floor snapshots, guest admissions/knocks and rate-limit maps. These reset on backend restart.
  • Only on device: guest collection/achievements/stats, local event baselines, UI preferences, daily room caches, guest profile and account offline caches. Clearing Electron localStorage can lose guest progress.
  • Room chat and guest DMs have no durable server history. Backing up PostgreSQL does not preserve guests’ device collections.

Migrations and access

Startup runs the idempotent schema.sql statements sequentially. RLS is enabled on all game tables with no public policies. The backend needs the owner/BYPASSRLS context or an explicitly designed database access policy; a Supabase anon key is not a game-admin credential. The recorded installation uses the database-owning workshop role.

The backend loads its production connection string from /etc/zeus-workshop.env. Owner database credentials have also been included in the Database access chapter at your request. Brevo secrets remain on the server. Normal event administration requires shell/database access; there is no public SQL or owner-write API.

A row being present in live_events does not guarantee it can run: runtime parsing also enforces supported IDs, targets, crews and existing reward definitions. Unknown reward items or title strings make the entire event definition invalid.

The service uses Node’s native HTTP server, ws for WebSockets, pg for SQL and dotenv for server configuration. No separate Redis, queue, scheduled worker or server physics simulator appears in this implementation.

Real-time transport

The client connects to /socket, sends hello with device/session/name/token, then join with a room id. Commands include knock, moderate, packet, dm and history. Notices include joined, waiting, snapshot, directory, knocks, packet, dm, history, social and notice.

Gameplay messages include state, present drop/open, bell, chat, emote, snowball, item drop/claim/grant, found and trade. Session IDs and monotonic sequence numbers reject stale/replayed packets within a connection. Signed-in names and moderation identity are supplied by the server.

Movement updates are sent about every 60 ms while active, with fuller state about every 900 ms. A peer unseen for 5 seconds can disappear locally. Cloud reconnection normally waits 5 seconds; replacement or authentication closes do not auto-retry. Identity/session validity is refreshed every 5 seconds.

The protocol module still contains legacy multicast constants 239.255.77.88 and UDP 47823. The inspected Floor transport uses cloud WebSockets; those constants do not describe the deployed connection path. RFID TCP services (for example Fixed 12352, Handheld 10472 and OCR 10482) belong to the emulator features and are separate from the Workshop HTTP/WebSocket service.

The 15-second heartbeat is an interval, not a guaranteed 15-second stale-client removal bound: a missing response is checked on a subsequent tick. The client has its own 20-second quiet-link watchdog.

Run one backend instance. Multiple instances would split presence, moderation queues, floor objects and room trees because there is no shared pub/sub layer. More CPUs or a load balancer alone do not fix this. The recorded 1 GB/1 CPU allocation has no verified load-test envelope.

Origin allowlists cover packaged null/file origins and local Vite. HTTPS transport and authentication protect connections; CORS alone is not authorization. Behind a proxy, rate limits using req.socket.remoteAddress may group many players under the proxy IP.

Live events

Live events

Live events are database-configured banners, challenges and opt-in activities executed by the existing client/server runner. They are not arbitrary scripts, new game modes or streamed video events.

Supported kinds

Supported metrics

MetricExact counter meaning
sendsSuccessful tag-send batches, including Handheld batches.
handheldSuccessful Handheld broadcast rounds; also included in sends.

tradesCompleted trades, one per completed trade.

Definition fields and validation

  • id: unique 1–80 character token using letters, digits, underscore or hyphen. Use a NEW ID for each event edition.
  • title is displayed up to 100 characters; body up to 1,000. No executable JavaScript is accepted.
  • start_at/end_at: timestamptz with end strictly after start. enabled must be true and server time must lie in [start,end). Prefer explicit UTC offsets for scheduled events.
  • target: positive integer, accepted by runtime up to 10,000,000.
  • crews: SQL NULL means everyone. A JSONB array such as ["QA","EDGE"] restricts eligibility. An empty array means no crew qualifies.
  • reward: SQL NULL or JSONB with an existing item id and/or an allowlisted title string. Example {"item":"angel-wings","title":"Tag Trader"}. Arbitrary new titles cannot be used as event rewards.
  • opt_in controls the Join requirement; kind opt-in also forces opt-in behavior in the parser. Keep the fields consistent. pairing can be same-crew or NULL. Pairing is meaningful with opt-in events.

Activation, progress and rewards

There is no event creation/editing endpoint or owner panel. An owner edits live_events through PostgreSQL. A compatible installed client can discover new event rows without rebuilding or restarting the service. Adding new sprites, item IDs, metrics or event logic requires code changes and compatible releases.

Events are fetched when opening the shared Workshop and every 60 seconds. Expiry is also evaluated locally every second, so a cached banner can disappear during an outage. A newly enabled/disabled definition can take a poll interval to update; reopening the Workshop triggers another fetch. Home does not poll events.

For a challenge, baseline is the profile stat at the first server observation, not necessarily the counter at the published start time. Opt-in resets baseline once at joining. Value is monotonic: max(previous progress, current stat minus baseline). Progress is per account, not a shared group goal.

The backend evaluates events after profile sync and on authenticated GET /events. It locks the profile and grants each reward once transactionally using event_progress.rewarded. Merely reading authenticated /events can therefore write progress or issue rewards. There is no manual claim endpoint.

Stats come from client-submitted profiles. The service does not independently verify RFID sends, trades, gift recipients, loot rolls or movement. These events suit a trusted casual group; high-value prizes would require stronger server-side action validation. Unsynced actions near the closing time can miss the active window; allow time for sync and verify completion before ending.

Guests see eligible definitions, track a local device baseline and can locally opt in, but receive no cloud reward. Their selected local crew is for display eligibility. Their progress does not create event_progress account records.

Secret Santa behavior

Set kind=opt-in, metric=given, target=1, opt_in=true, pairing=same-crew. Signed-in waiting participants are paired two at a time within their current crew when people join. The waiting list sorts by account creation time/id; it is not a randomized draw or a one-way gift cycle. Existing pairs stay stable.

One participant or an odd final participant remains unmatched until another joins. The UI shows the recipient’s display name, not a unique handle. Progress still uses the general given counter. The implementation does not require the recipient to match the assigned partner, and does not gate reward completion on a successful pair. Organizers must coordinate actual gift delivery socially.

The built-in Secret Santa achievement (give three items) is separate from any database Secret Santa event (for example give one item after joining). One does not automatically create the other.

Reruns and cancellation

Use new IDs for reruns: progress, opt-in state, baselines, pairing and rewarded flags are keyed by event ID. Re-enabling an old row resumes its old state rather than creating a clean edition.

Disable with UPDATE live_events SET enabled=false WHERE id=... . Existing rewards remain in bags; disabling is not a rollback. Avoid deleting an event if you need progress history: its event_progress rows cascade-delete. Setting end_at=now() for a not-yet-started event can violate the end-after-start check, so disabling alone is the safe general cancellation command.

Owner runbook

Owner runbook

Commands here are instructions for an authorized administrator; none were executed against production during this investigation. The composer produces reviewable SQL without making requests.

Run an event from preparation to close

  • Confirm LAN backend, public HTTPS and a real two-player WebSocket connection. Check signup delivery if new players need accounts.
  • Choose a unique event ID, kind, eligible crews, valid metric, target, time window and an existing reward. Use a test edition first.
  • Take a PostgreSQL backup. Insert the event DISABLED, inspect it, then enable with the intended window.
  • Verify /events and the banner in a compatible client. For account challenges, open before actions so the baseline exists. For opt-in, Join before starting.
  • Complete a small test, wait for account sync, and verify event_progress.value/rewarded plus the actual collection. Test an ineligible crew and a guest if relevant.
  • For a larger audience, split across crew rooms; clients only render 24 peers. Arrange Kings in advance if visitors must knock.
  • Monitor progress with SQL; do not poll authenticated event endpoints as though they were guaranteed read-only.
  • Disable when required and preserve the rows for history. Export summary counts and back up again. Rewards are not revoked automatically.

Monitor event progress — inside psql

SELECT e.id,e.title,e.enabled,e.kind,e.metric,e.target,
       e.start_at,e.end_at,count(p.user_id) AS observed_accounts,
       count(*) FILTER (WHERE p.opted_in) AS joined,
       count(*) FILTER (WHERE p.rewarded) AS rewarded
FROM live_events e LEFT JOIN event_progress p ON p.event_id=e.id
GROUP BY e.id ORDER BY e.start_at DESC;

SELECT u.handle,u.crew,p.value,p.baseline,p.opted_in,p.rewarded,
       recipient.handle AS recipient
FROM event_progress p JOIN users u ON u.id=p.user_id
LEFT JOIN users recipient ON recipient.id=p.recipient_id
WHERE p.event_id='REPLACE_EVENT_ID' ORDER BY p.value DESC;

UPDATE profiles SET titles=titles || '["Workshop Champion"]'::jsonb
WHERE user_id=(SELECT id FROM users WHERE handle='REPLACE_HANDLE')
AND NOT titles @> '["Workshop Champion"]'::jsonb;

Limits & gaps

Limits & gaps

These findings distinguish observed failures, code-level limitations and historical deployment claims. They are relevant before promising events, rare rewards or a large audience.

Current access gap

The LAN backend and its event query worked. Both Windows HTTPS and Node fetch to the public URL failed at TLS/connection level; the public hostname did resolve. This does not prove all players are offline, nor that PostgreSQL is down. Proxmox SSH access subsequently succeeded using the supplied login. The database credentials and container-local PostgreSQL listener were inspected, and the local SSH tunnel passed a read-only SQL connection check. Public Funnel status, backups and production gameplay rows have not been audited.

Confirmed source mismatches

  • Java Engineer achievement: checks discovery ID java-king, while the catalog defines java-king-coffee. A direct evaluation with the actual coffee item still returned progress [0,1]. Automatic unlock is broken for that item in this checkout.
  • QA title loot gating: title-qa requires minTags=500, but openPresent calls rollItem with no tagCount, defaulting to 0. Ordinary present opening excludes that item even after a large send. Avoid promising it as a normal large-batch drop until fixed; an explicit valid event reward can still grant the known item.
  • Capacity: the server accepts up to 512 sockets, but a client stops adding peers after 24. A single giant room will not display everyone.
  • Floor lifetime differs: client presents can last 10 minutes, but the backend caches floor entries for only 2 minutes. Rejoining or late-arriving players can see a different floor.
  • Heartbeat documentation says a 15-second detection window, while implementation checks missing pongs on a later 15-second tick; use a wider operational expectation.

Trust and operations limits

  • Client-side loot/stat/trade simulation means the backend is not an authoritative anti-cheat game server. Atomic reward issuance does not validate the gameplay that earned it.
  • Secret Santa pairs are advisory: no recipient proof, no randomized draw, and progress can increase while unmatched.
  • No distributed room state, automatic failover, database migration rollback framework or independent event scheduler appears in the service.
  • No recurring event definition: separate editions need new rows and unique IDs. No shared total/leaderboard objective or arbitrary metric plugin exists.
  • No confirmed current backup schedule, production row counts, installed PostgreSQL version, current online-player census or deployed-source hash was available.
  • New or invalid reward IDs/titles can silently hide events. Newer item IDs may be discarded by older clients’ allowlist parsers, so mixed client versions matter.
  • Brevo sender, API key and authorized source IP are dependencies for signup. A home public-IP change can break email if provider authorization is tied to that IP. Existing sign-in and guest play do not require a new verification delivery.
  • The source’s reported 387 historical passing tests and high-FPS measurements are deployment notes. Today’s fresh verification was the focused 68-test suite, not a new full-suite run or load test.

Before a substantial live event

  • Restore public reachability and test from an external network.
  • Confirm the exact client build and backend bundle are compatible.
  • Back up and confirm an off-device restore path.
  • Run a tiny complete test event using its own ID.
  • Plan rooms around rendered-peer limits and assign any necessary Kings.
  • For valuable prizes, add server-side validation and audited transfer/progress records before relying on current counters.
